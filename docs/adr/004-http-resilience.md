# 4. Полный HTTP-тайм-аут и ошибки шлюза

Статус: принято.

Настройки клиента Hotel находятся в `HotelClientProperties`. `HotelEndpointResolver` выбирает адрес по Eureka либо явному URL. `HotelCallPolicy` отвечает за Retry и два независимых Circuit Breaker. `HttpHotelClient` формирует команды, проверяет ответы и освобождает резерв по `bookingId`.

Ожидание результата `sendAsync(..., BodyHandlers.ofString())` ограничено временем на полный ответ. При тайм-ауте или прерывании future отменяется. Это принципиально для случая, когда сервер уже прислал заголовки, но задержал тело: один только `HttpRequest.timeout` в используемом JDK не покрывал этот сценарий. Ограничение проверяется тестом `timeoutIncludesBodyAfterHeadersHaveArrived`.

По умолчанию сетевые ошибки и ответы 429/5xx повторяются до трёх попыток с экспоненциальной задержкой. На получение полного ответа отводится 2 с на попытку. Проверка `bookingId`, номера и статуса ответа выполняется внутри той же политики: некорректное подтверждение также считается неудачным вызовом. Бизнес-отказы 4xx не повторяются и не размыкают Circuit Breaker. Формат их тела не меняет окончательный характер статуса.

Для компенсаций используется отдельная цепь: недоступность создания брони не блокирует освобождение. Неудачное освобождение сохраняется в Booking и повторяется обработчиком восстановления. Сквозной `integration-test.py` проверяет эту цепочку с настоящими БД и HTTP между сервисами.

Gateway имеет общий `ErrorWebExceptionHandler` и единый JSON writer для ошибок транспорта, маршрутизации и безопасности. Gateway возвращает 503 при отказе соединения, 504 при тайм-ауте и 404 для неизвестного маршрута. Формат соответствует `ApiError`. `X-Request-Id` возвращается и на ошибках. Событие запроса логируется при фиксации ответа, поэтому содержит окончательный HTTP-статус.
